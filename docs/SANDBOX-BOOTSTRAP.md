# Finance Tracker sandbox bootstrap proposal

This Step 1 proposal defines a disposable environment for the [approved spec](SPEC.md). It uses the checked-in SQL and the dated, metadata-only evidence in [Connection inventory](CONNECTIONS.md). Bootstrap, browser smoke tests, and performance measurements are pending.

## Isolated local preview

1. Use the Supabase CLI and a Docker-compatible runtime in a dedicated scratch directory. Record the CLI, container runtime, and stack versions. Give the instance its own local project ID and ports. Start it unlinked, with loopback-only listeners, and verify the instance identity, API/DB destinations, and port bindings before applying SQL. Use local targets explicitly for database commands. Abort if any target is unknown or points to the personal project. [Supabase local development guide](https://supabase.com/docs/guides/local-development)
2. After the versioned bootstrap is reviewed and replayed, build and start the app locally from a clean environment. Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` to this stack's API URL and compatible public key before building. Keep production credentials out of the process and browser. Check the built app's actual request origins before signing in or writing. Set Auth site URL and redirects to the local app origin and use the local mail catcher for confirmation. Keep `GROQ_API_KEY` unset. Leave `SUPABASE_SERVICE_ROLE_KEY` unset for the core smoke test. If an approved OAuth test needs it later, use only the sandbox key on the server for OAuth bookkeeping.
3. Use a clean browser profile and two disposable identities created through normal signup and confirmation. Perform desktop and narrow emulated checks locally. If a physical phone or remote browser needs access, use an authorized, protected preview with a separately approved non-production Supabase backend reachable by both the browser and server. Scope its environment variables to that preview, validate both effective targets before testing, and keep existing deployment protection. Keep the local stack private. Verify reachability and any cost before provisioning hosted resources.

## Schema replay

The root SQL files are historical inputs for review. The proposed bootstrap should use versioned migrations and an empty Supabase stack with `auth.users` and `auth.uid()` available. Use schema metadata to confirm exact types, defaults, nullability, constraints, indexes, triggers, extension placement, grants, policies, and API exposure. The field list in the spec is insufficient to derive those definitions on its own.

| Order | Source or prerequisite | Review before replay |
| --- | --- | --- |
| 1 | Supabase Auth, UUID generators, and missing `public.transactions` base DDL | Verify that `gen_random_uuid()` and the `uuid_generate_v4()` used by action logs resolve in the migration context, including the `uuid-ossp` extension where needed. Obtain metadata-only transaction DDL for `id`, `created_at`, `title`, `amount` and `type`, including the allowed `income` / `expense` values. Reconcile ownership with the next migration. |
| 2 | [Multi-user migration](../supabase_migration.sql) | Creates wallets and their per-user slug uniqueness, adds nullable transaction `user_id` and enables ownership RLS. Exclude the commented personal-account backfill and wallet inserts. Seed only disposable users through test setup. |
| 3 | [Actions](../supabase_migration_actions.sql), [analysis](../supabase_migration_ai.sql), [chat v1](../supabase_migration_chat.sql) | These three can follow Auth and UUID setup independently. Check policies, the unique analysis row per user, and supported message roles. |
| 4 | [Chat v2](../supabase_migration_chat_v2.sql) | Requires chat v1. Creates sessions and user memory, adds the session foreign key, then backfills legacy messages. Test the backfill separately with synthetic legacy messages. The session ID FK alone does not enforce shared ownership. Attempt foreign-session inserts and reassignments and record any denial failures for Step 2. |
| 5 | [OAuth](../supabase_migration_oauth.sql) | Can follow Auth independently. Clients precede codes and tokens. Verify RLS with no public policies and explicitly check Data API access as anonymous and authenticated roles. Use empty OAuth tables for core smoke. |

Review grants separately from RLS. Check API role access with real user sessions. A successful admin query or enabled RLS flag alone leaves that access unverified. Keep production-only `ai_write_requests`, `create_ai_transaction_once` and `execute_ai_write_once` outside the sandbox app baseline pending the Step 2 retention decision. Record this difference in the schema comparison. Review and replay each migration once in order, then verify reproducibility by rebuilding from scratch. Several historical policy declarations are unconditional and can fail when applied twice against the same schema.

## Two-user smoke and recovery

1. In separate browser profiles, sign in as A and B. Confirm wallet initialization and isolation. As A, create and edit a disposable transaction, cancel another draft, navigate away and back, and reload. Check the persisted ledger, balances, and history. Use a test-only request failure to exercise retry and double-click. Record any duplicate, partial write, false success, or lost draft as a baseline failure.
2. Repeat the owner path as B. Using ordinary authenticated API clients, use each identity against the other's known fixture IDs. Cover reads, update/delete, inserts with a foreign `user_id`, owner reassignment, and applicable chat/session and history ownership cases. Check unauthenticated access and direct OAuth table access as both roles. A denied update/delete can return zero affected rows. Re-read as the owner and verify absence of disclosure or mutation. Record any case that needs later implementation, including foreign IDs in history payloads.
3. Exercise invalid credentials and sign-out. Reload a protected deep link and verify session recovery or a return to login. Record exact app commit, schema revision, environment, attempted cases, observed outcomes, and blockers. Use disposable records for all writes.
4. On a migration or setup failure, stop the app, identify the first failing step, correct the local bootstrap, and replay against the known disposable instance from scratch. If diagnosis requires keeping a snapshot, retain only synthetic local state. After confirming the instance identity and that nothing needs preservation, use the CLI's explicit local reset to recreate it from reviewed migrations, or remove just that instance's containers and volumes. Never pass a remote target to a reset. [Supabase reset reference](https://supabase.com/docs/reference/cli/supabase-db-reset)

For rollback rehearsal, restore a known-good app build and schema revision together, recreate the disposable fixtures, and rerun the smoke tests. Reverting an app build leaves database state in place. Any future production migration needs separate owner authorization and a reviewed, rehearsed backup and recovery plan for schema and data.

## Representative performance fixtures

- Use a deterministic synthetic generator with recorded seed and timezone. Use small and above-row-cap histories, such as 50 rows and at least twice the verified local API cap for one user. Add a smaller second-user ledger for isolation. Include income, expenses, multiple wallets, balanced transfers, open and completed debts, same-timestamp rows around page boundaries, and dates spread over months. Use the app's existing title encoding. Compute independent expected counts and totals for each fixture, and verify balances and analytics against them before comparing timings.
- Use production-mode builds from the baseline and candidate commits. Keep device, browser, dataset, route sequence, app/backend placement, throttling, timezone, and tracing method fixed. Measure cold login/deep-link load separately from warm navigation through Home, Transactions, Debts, Wallets, and Analytics. Record the route timing boundary (user action to correct ledger content), run count, median and tail (for example p95 from 30 or more runs), long tasks, render work, request counts, and transferred bytes. Separate optional AI traffic and redact headers, tokens, and record contents from retained traces.
- Flag missing rows, stale totals and retries. A truncated response can look faster while returning incorrect results. Report local timing as local evidence and mobile emulation separately from physical-device results. Hosted latency and quotas can differ. Derive budgets only after repeatable measurements and correctness checks exist. The fixture sizes above are proposed test conditions, and this document supplies no measured baseline.
